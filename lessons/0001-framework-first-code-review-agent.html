读懂 issue 中的框架术语

这一课只做一件事：解释 issue #2004 中反复出现的框架词。学完后，你应能说清楚这些词分别指向什么背景知识，而不是照着课程实现方案。

术语层次

issue #2004 涉及的框架背景可以分成下面几层：

Runner LLMAgent Skill PermissionPolicy CodeExecutor Storage Telemetry

Runner 是一次 run 的外层执行器，关联 session 和事件流；LLMAgent 是可挂载模型、工具、Skill 和 executor 的 Agent 类型；Skill 用 SKILL.md、docs、scripts 表达可复用工作流；PermissionPolicy 表示工具执行前的治理决策；CodeExecutor 提供隔离 workspace 和程序执行抽象；Storage 与 Telemetry 分别对应可查询记录和运行观测。

三条容易混淆的边界

skill_load 不是执行脚本

Skill 文档说明，skill_load 加载 SKILL.md 正文和选定 docs；脚本执行发生在 workspace 中，通常通过 workspace_exec。

WithCodeExecutor 不是自动跑所有代码块

配置 executor 让 execution tools 可用；Markdown fenced-code auto-execution 是另一个独立开关。理解这点能避免把“有 executor”和“自动执行回复里的代码块”混为一谈。

local executor 不是默认生产方案

Skill 文档明确 local fallback 是开发便利。issue 要求 container 或 E2B workspace runtime；本地 runtime 只能作为 fallback。

背景知识分层

层 你需要理解的问题
框架层 Runner、LLMAgent、Tool、Skill、Workspace、Session 在框架中各自是什么。
代码评审层 finding、severity、confidence、evidence、recommendation、rule_id 为什么要结构化。
Go 工程层 unified diff、Go package、hunk 行号、go test、go vet、Staticcheck 的语义。
安全治理层 沙箱、权限决策、环境变量白名单、输出限制、脱敏、artifact 限制分别防什么风险。
审计存储层 task、sandbox run、permission decision、finding、artifact、report、metrics 为什么需要可查询。

练习

先自己回答，再展开答案。目标是检验你是否读懂术语边界。

1. 高风险命令应该由哪个组件先拦截？

PermissionPolicy 或安全 wrapper。deny / ask 不能继续进入沙箱执行；否则就变成“执行后记录”，不满足治理边界。

2. 自动 CR Agent 和 diff scanner 的概念差异是什么？

diff scanner 主要关注从变更文本中发现问题；issue 中的自动 CR Agent 还涉及 Skill、沙箱执行、Permission 决策、数据库记录、监控审计、artifact 和报告这些系统背景。

3. deterministic rule-only 是什么背景词？

它表示系统中一部分审查能力不依赖真实模型 API key，结果应可重复。理解这个词，是为了读懂验收标准对可测试性的要求。

4. 为什么脱敏不仅是报告格式问题？

因为 issue 同时要求报告和数据库不出现明文敏感信息。脱敏背景涉及持久化记录、artifact、中间审计数据和最终输出。
