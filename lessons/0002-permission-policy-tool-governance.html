PermissionPolicy 与工具治理

这一课只学通用框架 API：如何区分工具可见、工具自动执行、工具执行前审批。issue #2004 里的高风险命令治理，需要先掌握这三层边界。

先分清三件事

问题 框架机制 一句话
模型能不能看到这个工具？ ToolFilter 控制工具表面。
模型调用后框架是否自动执行？ ToolExecutionFilter 控制执行权归框架还是宿主。
这次具体调用是否允许执行？ PermissionPolicy 控制执行前审批。

这三层不要混用。隐藏工具不是审批；交给宿主执行也不是拒绝；审批通过才是 allow。

PermissionPolicy 的 API 形状

源码中 PermissionPolicy 只有一个核心方法：接收一次待执行 tool call 的 PermissionRequest，返回 PermissionDecision。

type PermissionPolicy interface {
    CheckToolPermission(
        ctx context.Context,
        req *tool.PermissionRequest,
    ) (tool.PermissionDecision, error)
}

常用写法是用 tool.PermissionPolicyFunc 或 agent.WithToolPermissionPolicyFunc 传入函数。

最小通用例子

下面的例子只演示框架 API，不绑定 issue #2004。它按 tool metadata 判断 destructive 工具是否需要审批。

func policy(
    _ context.Context,
    req *tool.PermissionRequest,
) (tool.PermissionDecision, error) {
    if req.Metadata.Destructive {
        return tool.AskPermission("approval required"), nil
    }
    return tool.AllowPermission(), nil
}

events, err := runner.Run(
    ctx,
    userID,
    sessionID,
    model.NewUserMessage("run the task"),
    agent.WithToolPermissionPolicyFunc(policy),
)

ask 和 deny 都不会执行工具。它们会把结构化结果返回给模型，让 assistant 能解释发生了什么。

如何读 PermissionRequest

ToolName

适合按工具名分支。例如只对执行类工具做额外检查。

Arguments

JSON 参数，已经过框架修复和 before-tool callbacks。适合解析命令、路径、环境变量。

Metadata

工具声明的安全属性。示例里用 Destructive 判断是否需要审批。

ToolCallID

和模型发出的具体 tool call 对齐。适合后续审计概念理解。

和 issue #2004 的关系

issue 提到“高风险命令必须先经过 PermissionPolicy 或安全 wrapper 决策”。这句话的背景是：执行类工具一旦放进 Agent 工具表面，模型可能提出具体调用；框架在真正执行前提供了 permission checkpoint。

这里你只需要掌握通用判断：allow 执行，ask 等待宿主审批且当前不执行，deny 拒绝且不执行。

练习

先在脑子里回答，再展开校验。

1. 想让模型完全看不到某个工具，用哪一层？

ToolFilter。它控制工具表面，也就是模型可见的工具集合。

2. 想让模型能调用，但不由框架自动执行，用哪一层？

ToolExecutionFilter。它让 run 在 assistant tool_call 后停下，由宿主执行并补回 tool message。

3. 想按这次调用的参数决定 allow / ask / deny，用哪一层？

PermissionPolicy。它在执行前拿到具体 tool call 的参数和 metadata。

4. ask 是不是会先执行工具再让用户确认？

不是。ask 表示当前不执行，并返回 approval required。真实审批 UI 应在 policy 内处理，批准后返回 allow。
