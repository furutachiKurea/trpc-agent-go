CodeExecutor 与 RunProgram

这一课学习隔离执行的最小 API：workspace、RunProgramSpec、RunResult、输入输出收集和 runtime capability。它解释“在沙箱里跑检查”这句话背后的框架知识。

先记住三个接口

接口 职责
WorkspaceManager 创建和清理 workspace。
WorkspaceFS 向 workspace 放文件、stage 输入、collect 输出。
ProgramRunner 在 workspace 中执行程序。

Engine 把这三者组合起来。EngineProvider 是 code executor 暴露底层 engine 的方式。

RunProgramSpec

RunProgramSpec 描述一次程序执行请求：

spec := codeexecutor.RunProgramSpec{
    Cmd:     "go",
    Args:    []string{"test", "./..."},
    Cwd:     "work/repo",
    Timeout: 2 * time.Minute,
    Env: map[string]string{
        "GOFLAGS": "-mod=readonly",
    },
}

关键字段包括命令、参数、环境变量、相对 workspace 的 cwd、stdin、timeout 和资源限制。是否支持干净环境，要看 runtime 的 capability。

RunResult

RunResult 是程序执行结果：

res, err := runner.RunProgram(ctx, ws, spec)
if err != nil {
    // runtime 层失败
    return err
}
if res.TimedOut {
    // 程序超时
}
if res.ExitCode != 0 {
    // 程序自己返回非零退出码
}
_ = res.Stdout
_ = res.Stderr

非零 ExitCode 通常不是 Go error。要检查 RunResult，不能只看 err。

输入和输出

InputSpec

把外部输入映射进 workspace。来源可以是 artifact://、host://、workspace://、skill://。

OutputSpec

声明要收集的输出 glob、最大文件数、单文件大小、总大小、是否保存 artifact、是否 inline。

Collect

按模式读取 workspace 文件。读取可能被截断，结果中有 Truncated 标志。

SaveArtifact

把 workspace 中的文件持久化为 artifact 引用，便于后续 turn 或外部系统引用。

SupportsCleanEnv 是什么

Capabilities.SupportsCleanEnv 不是你日常直接调用的 API。它是 executor 对框架说的一句话：我能不能在执行命令时丢掉宿主环境变量，只使用框架明确传入的环境。

你真正会写的是这类配置：

exec := localexec.New()

agt := llmagent.New(
    "worker",
    llmagent.WithModel(modelInstance),
    llmagent.WithCodeExecutor(exec),
    llmagent.WithWorkspaceExecAllowedCommands("go", "git", "cat", "sed"),
    llmagent.WithEnableCodeExecutionResponseProcessor(false),
)

这段代码的用户含义是：允许模型通过 workspace_exec 在 workspace 里跑命令，但只允许跑白名单里的命令。因为你启用了命令白名单，框架会进入 policy mode。policy mode 不只检查命令名，还要求执行进程从干净环境启动。

所以 SupportsCleanEnv 是白名单/黑名单命令策略的安全前提。executor 支持它，命令才会运行；executor 不支持它，workspace_exec 会直接拒绝执行，而不是悄悄降级。

为什么命令白名单需要干净环境

只限制命令名不够。假设你允许 go test ./...，但子进程继承了宿主环境，环境里可能有危险变量：

BASH_ENV=/tmp/hook.sh
LD_PRELOAD=/tmp/inject.so
PATH=/tmp/fake-bin:$PATH

这种情况下，你以为模型只是在 workspace 里运行 go，实际启动链路可能先加载了宿主环境里的脚本、动态库或伪造命令。CleanEnv 的作用就是让被执行程序从干净环境启动，只带框架允许的环境变量和 workspace 基础变量。

从用户角度记这个规则就够了：

没有配置 workspace_exec 命令白名单/黑名单：
  SupportsCleanEnv 通常不是你需要关心的第一件事。

配置了 WithWorkspaceExecAllowedCommands / WithWorkspaceExecDeniedCommands：
  你选择的 CodeExecutor 必须支持 CleanEnv，否则 workspace_exec 会失败。

它和 Workspace 的关系

Workspace 解决“在哪里执行”：本机临时目录、容器目录或远程沙箱目录。CleanEnv 解决“执行时带什么环境变量”。这两个问题是并列的，不是同一个概念。

概念 含义
Workspace 命令在哪个隔离工作区里跑，文件从哪里读、往哪里写。
RunProgramSpec.CleanEnv 这次命令是否应该从干净环境启动。
Capabilities.SupportsCleanEnv 当前 executor 是否真的能兑现“干净环境启动”。

和 issue #2004 的关系

issue 中的“沙箱执行需要有超时、输出大小限制、环境变量白名单、artifact 限制和失败记录”，对应的背景知识分别落在 RunProgramSpec.Timeout、OutputSpec、CleanEnv / env policy、artifact collection 和 RunResult / error handling 上。

练习

1. 命令退出码是 1，err 一定非 nil 吗？

不一定。非零退出码通常在 RunResult.ExitCode 中表达，runtime 层失败才更可能是 Go error。

2. 输出文件太大应该靠什么背景概念理解？

OutputSpec.MaxFileBytes、MaxTotalBytes、Collect 的 truncation，以及 artifact 限制。

3. 什么时候你需要关心 SupportsCleanEnv？

当你给 workspace_exec 配置命令白名单或黑名单时。它表示当前 executor 是否能让命令从干净环境启动；不支持时，框架应拒绝执行。
